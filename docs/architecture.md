# Architecture

The lab models an at-least-once validation pipeline without relying on private
systems or datasets.

```text
deterministic generator
          |
          v
   Queue interface -------- optional future AMQP adapter
          |
          v
       workers ---- validation fingerprint
          |
          v
    Store interface ------- PostgreSQL implementation
          |
          v
 unique message_id result
```

## Delivery contract

1. A producer assigns a stable message ID to each synthetic endpoint.
2. A worker receives and validates the JSON payload.
3. Validation or persistence failures are negatively acknowledged and requeued
   within a configured attempt budget.
4. Malformed payloads are negatively acknowledged without requeueing.
5. Exhausted retries move to an inspectable dead-letter sink.
6. A successful insert, or an already-present message ID, is acknowledged.

The primary key on `message_id` is the idempotency boundary. A retry may repeat
validation, but it cannot create a second durable result.

## Adapter boundaries

- `queue.Queue` isolates delivery semantics from a broker.
- `store.Store` isolates idempotent persistence from a database.
- `validator.Validator` makes validation policy independently testable.

The default executable intentionally selects the in-memory adapters. The Compose
file supplies RabbitMQ and PostgreSQL only as local infrastructure for adapter
experiments; it does not imply that those adapters or any benchmark against them
have been completed.

## Public-safety boundary

All identifiers, tenants, versions, regions, and payloads are generated by this
repository. The design is generic and does not reproduce any employer schema,
configuration, telemetry, customer information, or internal benchmark.
